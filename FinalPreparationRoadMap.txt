jstack — Thread Dump
------------------------

What is it?

A thread dump is a snapshot of all the threads running in a process 
(most commonly a Java Virtual Machine, or JVM) at a specific point in time. 
It shows what every thread is doing, making it one of the most useful tools for 
diagnosing performance and concurrency issues.

What information does a thread dump contain?

A thread dump typically includes:

Thread name (e.g., http-nio-8080-exec-1)
Thread ID
Thread state, such as:
RUNNABLE – actively running or ready to run
BLOCKED – waiting for a lock held by another thread
WAITING – waiting indefinitely for another thread
TIMED_WAITING – waiting for a specified period
TERMINATED – thread has finished execution
Stack trace – the sequence of method calls currently being executed
Lock information – which locks the thread owns or is waiting for
Example
"Worker-1" #23 prio=5 os_prio=0 tid=0x00007f8b3400
   java.lang.Thread.State: BLOCKED (on object monitor)
    at com.example.Account.withdraw(Account.java:45)
    - waiting to lock <0x000000076b0d1234>
    at com.example.Bank.transfer(Bank.java:78)

This indicates:

Thread name: Worker-1
State: BLOCKED
It's waiting to acquire a lock before it can continue.
The code causing the block is in Account.withdraw().
Why are thread dumps useful?

Developers and system administrators use thread dumps to diagnose issues like:

Application hangs – Determine why the application has stopped responding.
Deadlocks – Find threads waiting on each other indefinitely.
High CPU usage – Identify threads consuming excessive CPU.
Performance bottlenecks – Locate slow or blocked operations.
Thread leaks – Detect an unusually large number of active threads.
How to generate a thread dump (Java)

Some common methods are:

jstack <PID> – Generates a thread dump for a running JVM.
jcmd <PID> Thread.print – Prints thread information.
Press Ctrl + \ (on Unix/Linux) if the JVM is attached to a terminal.
Send kill -3 <PID> (Linux/macOS), which writes the thread dump to the application's standard output or log.
Use monitoring tools like VisualVM, JConsole, or Java Mission Control.
When should you take a thread dump?

Take one when:

The application is frozen or unresponsive.
CPU usage is unusually high.
Requests are taking much longer than expected.
You suspect a deadlock or thread contention.
Threads appear to be leaking.

For intermittent issues, it's common to capture multiple thread dumps (for example, 3 dumps 10–15 seconds apart). 
Comparing them helps determine whether threads are making progress or are stuck in the same state.

 ** How to Create Immutable Class
 
public final class Employee {

    private final int id;
    private final String name;

    public Employee(int id, String name) {
        this.id = id;
        this.name = name;
    }

    public int getId() {
        return id;
    }

    public String getName() {
        return name;
    }
}


Important rules:
 
Rule 1 : Make class: final
Rule 2 : Fields: private final
Rule 3 : No setters.
Rule 4 : Initialize fields through constructor.
Rule 5 : Defensive copying for mutable fields.


 ** Defensive Copy

This is senior-level interview material.

Suppose:

class Employee {

    private final Date joiningDate;

    public Employee(Date joiningDate) {
        this.joiningDate = joiningDate;
    }

    public Date getJoiningDate() {
        return joiningDate;
    }
}

This is not truly immutable.

Why?

Date is mutable.

Caller can do:

Date date = new Date();

Employee e = new Employee(date);

date.setTime(...);

Now the Employee's internal state changed.

** Correct Defensive Copy

public Employee(Date joiningDate) {
    this.joiningDate = new Date(joiningDate.getTime());
}

public Date getJoiningDate() {
    return new Date(joiningDate.getTime());
}

Now callers cannot directly modify the internal object.

With modern Java, prefer immutable date/time types such as:

LocalDate
LocalDateTime
Instant

where appropriate.

2. Control how data is changed

}

Interview level:

Why prefer composition over inheritance?

Suppose you write:

class Payment {

    void pay() {
    }

    void refund() {
    }
}


Then:
class CashPayment extends Payment {
}

But suppose your business rule says:  Cash payment cannot be refunded through the system.

A better design might be:

interface Payment {
    void pay();
}

and:

interface Refundable {
    void refund();
}

Then:

class CreditCardPayment implements Payment, Refundable {

    public void pay() {
    }

    public void refund() {
    }
}

while:

class CashPayment implements Payment {

    public void pay() {
    }
}

Now only refundable payments implement:

Refundable

This is capability-based design, and it naturally avoids many LSP problems.




You might end up doing:

"Explain Liskov Substitution Principle using the Bird/Penguin example."

A strong 8-year-experience answer would be:

LSP states that a subtype should be substitutable for its parent type without changing the correctness or expected behavior of the program.

For example, if Bird has a fly() method and Penguin extends Bird, then Bird bird = new Penguin(); bird.fly(); becomes problematic because penguins cannot fly.

The problem isn't that Penguin isn't a Bird. The problem is that Bird has been given a behavior that isn't applicable to all birds.

Instead, I would keep common behavior such as eat() in Bird and model flying as a separate capability, such as a FlyingBird interface. Then Eagle and Sparrow can implement FlyingBird, while Penguin doesn't.

This keeps the abstraction behaviorally correct and allows subtypes to safely substitute their parent types.

Remember this one line:

LSP is not about whether the child "IS-A" parent in the real world; it is about whether the child can safely behave like the parent in the software design.

## 7. Thread Lifecycle

A simplified Java thread lifecycle:

NEW
 │
 │ start()
 ↓
RUNNABLE
 │
 ├───────────────┐
 │               │
 │ waiting       │ lock/sleep/wait/join
 ↓               ↓
RUNNING       WAITING / BLOCKED / TIMED_WAITING
 │               │
 └───────────────┘
        │
        ↓
    TERMINATED

The important states are:


NEW
Thread thread = new Thread();

Thread object exists but hasn't started.

State = NEW


RUNNABLE

After:

thread.start();

The thread is ready to run or currently executing.

State = RUNNABLE

The OS scheduler decides when it actually gets CPU time.

BLOCKED

A thread is waiting to acquire a monitor lock.

Example:

synchronized(lock) {
    // critical section
}

If another thread already owns lock:

Thread 1
   │
   │ owns lock
   ↓

Thread 2
   │
   └── BLOCKED

WAITING

The thread waits indefinitely for another thread/action.

Examples:

object.wait();
thread.join();

TIMED_WAITING

The thread waits for a specific amount of time.

Examples:

Thread.sleep(5000);

thread.join(5000);
TERMINATED

The run() method has completed.

public void run() {

    System.out.println("Finished");
}

After completion:

State = TERMINATED

A terminated thread cannot be started again.

This will throw an exception:

Thread thread = new Thread();

thread.start();
thread.start();

You will get:

IllegalThreadStateException

9. sleep()

sleep() pauses the current thread.

Example:

public class SleepExample {

    public static void main(String[] args)
            throws InterruptedException {

        System.out.println("Started");

        Thread.sleep(3000);

        System.out.println("Finished after 3 seconds");
    }
}

Execution:

Started
   ↓
Thread sleeps 3 seconds
   ↓
Finished

Important:

sleep() does not release a synchronized lock.

Example:

synchronized (lock) {

    Thread.sleep(5000);
}

During those 5 seconds:

Thread owns the lock
       ↓
Other threads cannot enter

This is an important interview question.

10. join()

join() makes the current thread wait for another thread to finish.

Example:


package com.heg.phase1;

public class MyTaskV2 extends Thread {
	
	public void run() {
		for(int i = 1 ; i<=5 ;i++) {
			System.out.println("Worker : " +i);
		}
	}
	
	public static void main(String[] args) {
		MyTaskV2 task = new MyTaskV2();
		task.start();
		try {
			task.join();
		} catch (InterruptedException e) {
			// TODO Auto-generated catch block
			e.printStackTrace();
		}
		
		System.out.println("Main Finished");
	}

}

OUTPUT ::
Worker : 1
Worker : 2
Worker : 3
Worker : 4
Worker : 5
Main Finished


Execution:

Main Thread
    │
    │ start worker
    ↓
Worker Thread Running
    │
Main Thread calls join()
    │
    └──── WAITING ────┐
                      │
Worker finishes       │
                      ↓
Main continues

Without join(), output order may be unpredictable.


interrupt()

interrupt() is a request to a thread to stop what it is doing.

It does not forcefully kill the thread.

When all user threads finish:

 ↓

Thread.MAX_PRIORITY  // 10

Example:

But do not depend on priority for correctness.

For production applications:

import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

public class ExecutorExample {

    public static void main(String[] args) {

        ExecutorService executor =
                Executors.newFixedThreadPool(2);

        for (int i = 1; i <= 5; i++) {

            int taskNumber = i;

            executor.execute(() -> {

                System.out.println(
                    "Task " + taskNumber
                    + " running on "
                    + Thread.currentThread().getName()
                );

                try {
                    Thread.sleep(2000);
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
            });
        }

        executor.shutdown();
    }
}


The important point:

Worker threads do not die after one task. They take another task from the queue.

    System.out.println("Hello");

void

Use it when you only want to execute a task.


submit()

Future<Integer>

Simple comparison
| Feature                               | `execute()` | `submit()` |
| ------------------------------------- | ----------- | ---------- |
| Accepts `Runnable`                    | Yes         | Yes        |
| Accepts `Callable`                    | No          | Yes        |
| Returns result                        | No          | Yes        |
| Returns `Future`                      | No          | Yes        |
| Can cancel task                       | No          | Yes        |
| Exception accessible through `Future` | No          | Yes        |

After submitting tasks:

executor.shutdown();

It means:

Do not accept new tasks
          ↓
Finish already submitted tasks
          ↓
Stop worker threads


Example:

The last task will throw:

RejectedExecutionException

because the executor is shutting down.

Stop accepting new tasks
        ↓

        ↓
Remove tasks that have not started

Suppose 1,000 requests come to your application.

3. How does a Thread Pool work?

Suppose:

        Executors.newFixedThreadPool(2);

You submit 5 tasks.

Main Thread

             ↓
       ExecutorService
             ↓

     ┌─────────────────┐
     │ Thread Pool     │
     │                 │

import java.util.concurrent.Executors;

public class ThreadPoolExample {

5. execute() vs submit()

This is a common interview question.

execute()

    System.out.println("Hello");
});

Characteristics:

Accepts → Runnable
Returns → void

Use when you don't need a result.

submit()
Future<Integer> future =
        executor.submit(() -> {

            return 100;
        });

Characteristics:

Accepts → Runnable or Callable
Returns → Future

Use when you need:

Result
Task status
Cancellation
Exception handling

Feature	execute()	submit()

Returns value	No	Future

6. Important Difference: Exception Behavior

Look carefully.

execute()
executor.execute(() -> {

    throw new RuntimeException("Something failed");

});

The exception can be handled by the worker thread's uncaught-exception mechanism and may appear in logs.

With submit():

Future<?> future =
        executor.submit(() -> {

            throw new RuntimeException("Something failed");

        });

The exception is captured by the Future.

You need:

try {

    future.get();

} catch (Exception e) {

    System.out.println(e);
}

The original exception is typically available as the cause of ExecutionException.

7. shutdown() vs shutdownNow()
shutdown()
executor.shutdown();

Meaning:

Stop accepting new tasks
        ↓
Already submitted tasks continue
        ↓
Queued tasks execute
        ↓
Executor terminates when finished

Example:

Task Queue

Task 1 → Running
Task 2 → Waiting
Task 3 → Waiting

shutdown()
    ↓

Task 1 finishes
Task 2 executes
Task 3 executes
    ↓
Executor terminates
shutdownNow()
executor.shutdownNow();

Conceptually:

Stop accepting new tasks
        ↓
Try to interrupt running tasks
        ↓
Return tasks that never started

Important:

shutdownNow() does not guarantee that a running task immediately stops.

Your task must respond to interruption.

Example:

try {

    while (!Thread.currentThread().isInterrupted()) {

        doWork();
    }

} finally {

    cleanup();
}
8. awaitTermination()

After shutdown:

executor.shutdown();

You can wait:

boolean finished =
        executor.awaitTermination(
                10,
                TimeUnit.SECONDS
        );

Meaning:

Wait maximum 10 seconds
        ↓
All tasks completed?
        ↓
YES → true
NO  → false

A common shutdown pattern:

executor.shutdown();

try {

    if (!executor.awaitTermination(
            30,
            TimeUnit.SECONDS)) {

        executor.shutdownNow();
    }

} catch (InterruptedException e) {

    executor.shutdownNow();

    Thread.currentThread().interrupt();
}

This pattern gives running tasks a chance to finish gracefully.

13. corePoolSize vs maximumPoolSize

Example:

new ThreadPoolExecutor(
    2,
    10,
    60,
    TimeUnit.SECONDS,
    queue
);

Meaning:

corePoolSize = 2

Normally, the pool creates up to 2 core worker threads as tasks arrive.

maximumPoolSize = 10

If the queue cannot accept more tasks, additional threads can be created up to 10.

A common misunderstanding is:

"maximumPoolSize means the pool always creates 10 threads."

No.

It depends heavily on the queue type and capacity.

14. WorkQueue — Very Important

The queue stores tasks waiting for a worker.

ArrayBlockingQueue
new ArrayBlockingQueue<>(100);

Bounded queue.

Maximum 100 waiting tasks

Good because it gives backpressure through rejection when overloaded.

LinkedBlockingQueue

Can be bounded:

new LinkedBlockingQueue<>(100);

Or effectively very large/unbounded depending on construction.

Important production warning:

new LinkedBlockingQueue<>()

can grow very large, potentially consuming significant memory under sustained overload.

SynchronousQueue
new SynchronousQueue<>();

No internal capacity for normal task storage.

Conceptually:

Task
 ↓
Must hand off directly
 ↓
Worker

If no suitable worker can accept the task, the executor may create another thread up to maximumPoolSize, otherwise reject.

This behavior is why maximumPoolSize is particularly important with SynchronousQueue.

Example:

60,
TimeUnit.SECONDS

maximumPoolSize = 5

During heavy traffic:

5 threads created

Later traffic decreases.

Threads above the core size can become idle.

After:

60 seconds

idle non-core threads may be removed.

Back to:

High Traffic

    ↓

16. RejectedExecutionHandler

What happens when:

Threads = maximumPoolSize
Queue = Full

The task cannot be accepted.

Java provides rejection policies.

AbortPolicy
new ThreadPoolExecutor.AbortPolicy()

Result:

Reject task
    ↓
Throw RejectedExecutionException

Useful when failure should be immediately visible.

CallerRunsPolicy
new ThreadPoolExecutor.CallerRunsPolicy()

The calling thread executes the task.

Request Thread
     │
     │ Submit task
     ↓
Pool overloaded
     ↓
Request Thread executes task itself

This naturally slows down the producer and can provide a form of backpressure.

DiscardPolicy
new ThreadPoolExecutor.DiscardPolicy()
Task
 ↓
Silently discarded

Dangerous if tasks are important.

DiscardOldestPolicy
new ThreadPoolExecutor.DiscardOldestPolicy()

Conceptually:

Queue full

Remove oldest queued task
       ↓
Try submitting new task

Use only when dropping older work is acceptable.

NOTES ::
Why need ThreadPoolExecutor , We have ExecutorService alread ? 

Here is the breakdown of why you use them and how they fit together.

1. The Relationship (Interface vs. Implementation)
ExecutorService is an interface. It defines what actions can be performed (e.g., submit(), execute(), shutdown()). It doesn't care how those threads are managed or created.

ThreadPoolExecutor is a class. It implements the ExecutorService interface and provides the actual mechanics of 
how a thread pool works (managing a pool of worker threads, a blocking queue for tasks, 
thread recycling, and rejection policies).

Think of ExecutorService as a Vehicle interface (defining that it can drive, brake, and accelerate) 
and ThreadPoolExecutor as a specific type of vehicle, like a Tesla Model 3.

2. Why don't we just use ExecutorService directly?
You actually do use ExecutorService as your reference type in your code (which is a best practice for loose coupling), but you need a concrete class to instantiate it.

                        2,      // corePoolSize
                        4,      // maximumPoolSize
                        60,     // keepAliveTime
                        TimeUnit.SECONDS,
                        new ArrayBlockingQueue<>(2)
                );

        for (int i = 1; i <= 8; i++) {

            int taskNumber = i;

            try {

                System.out.println(
                    "\nSubmitting Task " + taskNumber
                );

                executor.execute(() -> {

                    System.out.println(
                        "START Task " + taskNumber
                        + " | Thread = "
                        + Thread.currentThread().getName()
                    );

                    try {
                        Thread.sleep(5000);
                    } catch (InterruptedException e) {
                        Thread.currentThread().interrupt();
                    }

                    System.out.println(
                        "END Task " + taskNumber
                    );
                });

                System.out.println(
                    "Pool Size = " + executor.getPoolSize()
                );

                System.out.println(
                    "Active Count = " + executor.getActiveCount()
                );

                System.out.println(
                    "Queue Size = "
                    + executor.getQueue().size()
                );

            } catch (Exception e) {

                System.out.println(
                    "Task " + taskNumber
                    + " REJECTED"
                );
            }
        }

        executor.shutdown();
    }
}

Step 7: Rejection Policies
When:

Maximum threads reached
        +
Queue full

Java needs to decide what to do.


1. AbortPolicy
new ThreadPoolExecutor.AbortPolicy()

Result:

Reject task
    ↓
Throw RejectedExecutionException


2. CallerRunsPolicy
new ThreadPoolExecutor.CallerRunsPolicy()

The thread submitting the task executes it.

Example:

Main Thread
     │
     │ submit Task 7
     ▼
Pool Full
Queue Full
     │
     ▼
Main Thread executes Task 7

This naturally slows down the producer.

This is a simple form of backpressure.


3. DiscardPolicy
new ThreadPoolExecutor.DiscardPolicy()
Task → silently discarded

Dangerous if the task is important.


4. DiscardOldestPolicy
new ThreadPoolExecutor.DiscardOldestPolicy()

Conceptually:

Queue Full

[Task 3, Task 4]

New Task 7
     ↓
Remove Task 3
     ↓
Try Task 7

Only use this when losing older work is acceptable.


| Policy                | What happens to new task? | Exception? | Existing queued task?      | Best use                         |
| --------------------- | ------------------------- | ---------- | -------------------------- | -------------------------------- |
| `AbortPolicy`         | Rejected                  | Yes        | No change                  | Critical tasks / detect overload |
| `CallerRunsPolicy`    | Caller executes it        | No         | No change                  | Backpressure, don't lose task    |
| `DiscardPolicy`       | Dropped                   | No         | No change                  | Non-critical tasks               |
| `DiscardOldestPolicy` | Added if possible         | Usually no | Oldest queued task removed | Latest data more important       |


What happens when a ThreadPoolExecutor is full?

When the worker count has reached maximumPoolSize and the work queue cannot accept another task, 
the executor invokes its RejectedExecutionHandler. Depending on the configured policy, it may 
throw RejectedExecutionException, run the task in the caller thread, discard the new task, 
or discard the oldest queued task and retry execution.

2. What is a Race Condition?
A race condition happens when multiple threads access shared mutable data, and 
the final result depends on the timing/order of execution.

package com.heg.mult.phase2;

class Counter{
	private int count = 0;
	
	public void increment() {
		count++;
	}
	public int getCount() {
		return count;
	}

public class RaceConditionExample {

	public static void main(String[] args) throws InterruptedException {
		Counter counter = new Counter();
		
		Thread t1 = new Thread(
				() -> {
					for(int i = 0 ; i< 100000; i++) {

					}

		Thread t2 = new Thread(
				() -> {
					for(int i = 0 ; i< 100000; i++) {
						counter.increment();
					}

		t2.start();
		
		t1.join();
		t2.join();

The exact wrong result can change each run.

That is a race condition.

7. What is a Monitor Lock?
Every Java object can be used as a synchronization monitor.

Conceptually:

Counter Object
┌──────────────────────────┐
│ count = 10               │

When you write:

you are saying:

Before entering this block, acquire the monitor lock associated with counter.

Only one thread can own that monitor at a time.

Instead of locking the entire method:

}

        count++;
    }
}

Consider:

    count++;
}

}

Then unrelated code can interfere with your locking.

Better:

This gives you more control.

13. Reentrancy

Java's synchronized locks are reentrant.

Example:

class Example {

    public synchronized void methodA() {

        methodB();
    }

    public synchronized void methodB() {

        System.out.println("Hello");
    }
}

When the same thread enters:

it already owns the object's monitor.

It can enter:

methodB()

without blocking itself.

Conceptually:

Thread-1 acquires lock
        ↓
methodA()
        ↓
methodB()
        ↓
Same thread allowed again

This is called:

Reentrant Locking

The lock is released only after the corresponding synchronized entries are exited.

Phase 7: Lock and ReentrantLock

1. Why Do We Need Lock?

synchronized is simple:

public synchronized void increment() {
    count++;
}

But sometimes we need more control.

For example:

Can I try to get the lock without waiting forever?
Can I wait only 5 seconds?
Can I cancel while waiting for a lock?
Can I use a fair lock?

synchronized does not provide these features directly.

So Java provides:

java.util.concurrent.locks.Lock


2. Basic Structure

The most common implementation is:

ReentrantLock
The most common implementation is:

ReentrantLock

Example:

import java.util.concurrent.locks.Lock;
import java.util.concurrent.locks.ReentrantLock;

class Counter {

    private final Lock lock = new ReentrantLock();

    private int count = 0;

    public void increment() {

        lock.lock();

        try {
            count++;
        } finally {
            lock.unlock();
        }
    }
}

The pattern is always:

lock.lock();

try {

    // Critical section

} finally {

    lock.unlock();
}




3. Why finally Is Extremely Important?

Consider:

lock.lock();

count++;

lock.unlock();

Suppose an exception occurs:

lock.lock();

throw new RuntimeException();

lock.unlock(); // Never reached ❌

The lock may remain held.

Other threads can keep waiting.

Potential result:

Thread-1
   │
   ├── Acquires lock 🔒
   │
   └── Exception ❌
        │
        └── Lock not released

Thread-2
   │
   └── Waiting forever

Correct:

lock.lock();

try {

    // Critical section

} finally {

    lock.unlock();

}

Even if an exception occurs:

Exception
    ↓
finally executes
    ↓
unlock()


4. What is ReentrantLock?

ReentrantLock means:

The same thread can acquire the same lock multiple times.

Example:

class Example {

    private final Lock lock =
            new ReentrantLock();

    public void methodA() {

        lock.lock();

        try {

            methodB();

        } finally {

            lock.unlock();
        }
    }

    public void methodB() {

        lock.lock();

        try {

            System.out.println("Hello");

        } finally {

            lock.unlock();
        }
    }
}

Flow:

Thread-1

methodA()
   ↓
Acquire Lock → Count = 1
   ↓
methodB()
   ↓
Acquire Same Lock → Count = 2
   ↓
unlock() → Count = 1
   ↓
unlock() → Count = 0
   ↓
Lock completely released

The same thread does not block itself.

This is:

Reentrancy

Behavior:

Thread wants lock
      │
      ▼

   ┌──┴──┐

  │       │
  ▼       ▼

Suppose you don't want a thread to wait indefinitely.

if (lock.tryLock()) {

    try {

        System.out.println("Lock acquired");

Thread
  ↓

   │

 │     │

7. tryLock(timeout) — Wait for Limited Time

Example:

try {

    if (lock.tryLock(5, TimeUnit.SECONDS)) {

        try {

            process();

        } finally {

            lock.unlock();
        }

    } else {

        System.out.println(
            "Could not acquire lock within 5 seconds"

Thread
   ↓

   ↓
Lock acquired?
   │
 ┌─┴─────┐
YES      NO
 │        │
 ▼        ▼

8. lockInterruptibly()

Normally:

A thread waiting to acquire the lock cannot use interruption in the same way as lockInterruptibly().

With:

lock.lockInterruptibly();

Example:

try {

    lock.lockInterruptibly();

    try {

        process();

    } finally {

        lock.unlock();
    }

} catch (InterruptedException e) {

    Thread.currentThread().interrupt();

    System.out.println("Lock wait interrupted");
}

Flow:

        │
        ▼

        │
        ▼

        │
        ▼

Useful for:

Responsive concurrent operations

| Fairness option                | No direct equivalent  | Yes                      |
| `Condition` objects            | `wait()/notify()`     | `Condition`              |
| Simplicity                     | Easier                | More flexible            |


10. Fair vs Non-Fair Lock

Create a normal lock:

Lock lock = new ReentrantLock();

By default:

Non-fair lock

You can create a fair lock:

Lock lock = new ReentrantLock(true);


Non-Fair Lock

Suppose:

Thread-2 waiting
Thread-3 waiting

The lock becomes available.

A newly arriving thread may acquire it before older waiting threads.

Conceptually:

Waiting:

T2 → T3

New:

T4

Lock released
      ↓
T4 may acquire first

Advantages:

Higher throughput
Less scheduling overhead
Fair Lock

With:

the lock favors granting access in roughly waiting order.

Conceptually:

      ↓
T3 waiting second
      ↓

      ↓

   ≠

Interview Questions
1. Why use ReentrantLock instead of synchronized?

ReentrantLock provides more explicit and flexible locking features such as tryLock(), timed lock acquisition, interruptible acquisition, configurable fairness, and Condition objects.

2. Why should unlock() be inside finally?

To guarantee that the lock is released even if the protected code throws an exception.

3. What is reentrancy?

The same thread can acquire the same lock multiple times without blocking itself. The lock is fully released only after matching unlock operations reduce the hold count to zero.

4. What is tryLock()?

It attempts to acquire a lock and returns immediately with true or false.

5. What is a fair lock?

A fair ReentrantLock favors longer-waiting threads when granting the lock, but fairness can reduce throughput.

6. Does ReentrantLock automatically release the lock?

No. You must explicitly call unlock(), normally inside a finally block.



Phase 8: ReadWriteLock and ReentrantReadWriteLock

In Phase 7, you learned:

synchronized / ReentrantLock
        ↓
Only one thread enters critical section

But what if your application has:

1000 READ operations
10 WRITE operations

For example:

Read product details
Read user profile
Read configuration
Read cache

Occasionally:
Update product
Update configuration
Update cache

If we use one normal lock for everything:

Thread-1 → READ 🔒
Thread-2 → WAIT ❌
Thread-3 → WAIT ❌
Thread-4 → WAIT ❌

Even though all threads are only reading.

This is where:

ReadWriteLock

becomes useful.

1. Main Idea

A ReadWriteLock has two different locks:

Read Lock
Write Lock

Conceptually:

                 ReadWriteLock
                       │
              ┌────────┴────────┐
              │                 │
              ▼                 ▼
          Read Lock         Write Lock

Rules:

Multiple Readers
        ↓
Allowed simultaneously ✅

One Writer
        ↓
Exclusive access ✅

Writer + Reader
        ↓
Not allowed simultaneously ❌

Writer + Writer
        ↓
Not allowed simultaneously ❌
2. Why Do We Need It?

Suppose we have a cache:

Map<String, String> cache = new HashMap<>();

Operations:

get() → Read
put() → Write

Imagine:

Thread-1 → get("user1")
Thread-2 → get("user2")
Thread-3 → get("user3")

All are only reading.

With a normal lock:

T1 → Read
T2 → Waiting
T3 → Waiting

This creates unnecessary waiting.

With ReadWriteLock:

T1 → Reading ─┐
T2 → Reading ─┼── Simultaneously ✅
T3 → Reading ─┘

Better concurrency for a read-heavy workload.


3. ReentrantReadWriteLock

The common implementation is:

java.util.concurrent.locks.ReentrantReadWriteLock

Basic example:

import java.util.concurrent.locks.ReadWriteLock;
import java.util.concurrent.locks.ReentrantReadWriteLock;

class DataStore {

    private final ReadWriteLock lock =
            new ReentrantReadWriteLock();

    private int data = 0;

    public int read() {

        lock.readLock().lock();

        try {

            return data;

        } finally {

            lock.readLock().unlock();
        }
    }

    public void write(int value) {

        lock.writeLock().lock();

        try {

            data = value;

        } finally {

            lock.writeLock().unlock();
        }
    }
}

The pattern is:

Reading
lock.readLock().lock();

try {
    // Read shared data
} finally {
    lock.readLock().unlock();
}
Writing
lock.writeLock().lock();

try {
    // Modify shared data
} finally {
    lock.writeLock().unlock();
}



4. How Multiple Readers Work

Suppose:

Data = "Hello"

Three threads call:

read();

Flow:

Time →

T1 ───────[ READING ]───────
T2 ───────[ READING ]───────
T3 ───────[ READING ]───────

All can execute together.

Why?

Because:

Read
+
Read
=
No data modification

Therefore concurrent reading is safe when the data access itself is correctly protected.

5. What Happens When a Writer Comes?

Suppose:

T1 → Reading
T2 → Reading
T3 → Wants to Write

The writer must wait:

T1 ───────[ READ ]────────────
T2 ───────[ READ ]────────────

T3 ─────────────── WAIT ──────► WRITE

The writer gets exclusive access only after existing readers release their read locks.

During writing:

T1 → Read ❌ Wait
T2 → Read ❌ Wait
T3 → Writing 🔒
T4 → Write ❌ Wait
6. Important Rule Table
Current Lock	New Read Request	New Write Request
No lock	Allowed	Allowed
Read lock held	Allowed	Wait
Write lock held	Wait	Wait
Write lock requested/waiting	Depends on lock policy and timing	Depends on lock policy and timing

Simple rule:

READ + READ = Allowed

READ + WRITE = Not allowed

WRITE + READ = Not allowed

WRITE + WRITE = Not allowed

8. Complete Multithreading Example
import java.util.concurrent.locks.ReadWriteLock;
import java.util.concurrent.locks.ReentrantReadWriteLock;

public class ReadWriteLockDemo {

    private static final ReadWriteLock lock =
            new ReentrantReadWriteLock();

    private static int value = 0;

    public static void main(String[] args)
            throws InterruptedException {

        Thread reader1 = new Thread(() -> read(),
                "Reader-1");

        Thread reader2 = new Thread(() -> read(),
                "Reader-2");

        Thread writer = new Thread(() -> write(100),
                "Writer");

        reader1.start();
        reader2.start();

        Thread.sleep(100);

        writer.start();

        reader1.join();
        reader2.join();
        writer.join();
    }

    private static void read() {

        lock.readLock().lock();

        try {

            System.out.println(
                    Thread.currentThread().getName()
                            + " reading value: " + value
            );

            Thread.sleep(3000);

        } catch (InterruptedException e) {

            Thread.currentThread().interrupt();

        } finally {

            lock.readLock().unlock();
        }
    }

    private static void write(int newValue) {

        lock.writeLock().lock();

        try {

            System.out.println(
                    Thread.currentThread().getName()
                            + " writing value: " + newValue
            );

            value = newValue;

        } finally {

            lock.writeLock().unlock();
        }
    }
}

Expected behavior:

Reader-1 reading value: 0
Reader-2 reading value: 0

... around 3 seconds later ...

Writer writing value: 100

Both readers can hold the read lock together.

The writer waits until both readers finish.

9. ReentrantReadWriteLock Is Reentrant

Just like ReentrantLock, the locks are reentrant.

Example:

class Example {

    private final ReentrantReadWriteLock lock =
            new ReentrantReadWriteLock();

    public void methodA() {

        lock.writeLock().lock();

        try {

            methodB();

        } finally {

            lock.writeLock().unlock();
        }
    }

    public void methodB() {

        lock.writeLock().lock();

        try {

            System.out.println("Hello");

        } finally {

            lock.writeLock().unlock();
        }
    }
}

Same thread:

Acquire Write Lock
        ↓
Call another method
        ↓
Acquire Write Lock again
        ↓
Allowed

The lock maintains a hold count.

10. Lock Downgrading

This is an important advanced concept.

Sometimes:

1. Acquire write lock
2. Update data
3. Continue reading updated data

Instead of completely releasing the write lock and then acquiring the read lock, you can downgrade.

Example:

ReentrantReadWriteLock lock =
        new ReentrantReadWriteLock();

lock.writeLock().lock();

try {

    updateData();

    lock.readLock().lock();

} finally {

    lock.writeLock().unlock();
}

try {

    readData();

} finally {

    lock.readLock().unlock();
}

Flow:

WRITE LOCK
     ↓
Update data
     ↓
Acquire READ LOCK
     ↓
Release WRITE LOCK
     ↓
Continue with READ LOCK

This is called:

Lock Downgrading

It helps maintain controlled access to the state while transitioning from writing to reading.

11. Lock Upgrading Problem

Now the opposite situation.

Suppose:

Thread acquires READ lock
        ↓
Reads data
        ↓
Decides:
"I need to modify it"
        ↓
Tries to acquire WRITE lock

Example:

lock.readLock().lock();

try {

    if (data == null) {

        lock.writeLock().lock(); // ⚠️ Dangerous

        try {
            data = createData();
        } finally {
            lock.writeLock().unlock();
        }
    }

} finally {

    lock.readLock().unlock();
}

Why is this dangerous?

Imagine:

T1 holds READ lock
T2 holds READ lock

T1 wants WRITE lock
        ↓
T1 waits for all readers

But T1 itself is still a reader!

It may wait indefinitely because it still holds its own read lock.

This is a lock upgrade problem.

Important rule
Do not try to upgrade directly:

READ LOCK → WRITE LOCK

Instead:

Release READ LOCK
        ↓
Acquire WRITE LOCK
        ↓
Recheck the condition

Example:

lock.readLock().lock();

boolean needsUpdate;

try {

    needsUpdate = (data == null);

} finally {

    lock.readLock().unlock();
}

if (needsUpdate) {

    lock.writeLock().lock();

    try {

        // Recheck!
        if (data == null) {
            data = createData();
        }

    } finally {

        lock.writeLock().unlock();
    }
}

Why recheck?

Because another thread may update the data between:

Release READ LOCK
        ↓
Acquire WRITE LOCK
12. Fair vs Non-Fair ReentrantReadWriteLock

Default:

new ReentrantReadWriteLock();

This creates a non-fair lock.

Fair version:

new ReentrantReadWriteLock(true);

Fair mode tries to honor waiting order more predictably.

Reader waiting first
Writer waiting second

Fair lock
    ↓
Earlier waiting thread is favored

But:

Fairness
    ↓
Potentially less throughput

Usually:

Default non-fair

is used unless your application has a specific fairness requirement.

13. Production Problem: Writer Starvation

Suppose your system is extremely read-heavy:

Reader-1 → Read
Reader-2 → Read
Reader-3 → Read
Reader-4 → Read
Reader-5 → Read
...

A writer arrives:

Writer → Waiting

Depending on contention and scheduling behavior, a writer can experience long delays.

16. Production Cache Example

Let's create a simple configuration cache.

import java.util.HashMap;
import java.util.Map;
import java.util.concurrent.locks.ReadWriteLock;
import java.util.concurrent.locks.ReentrantReadWriteLock;

class ConfigCache {

    private final Map<String, String> config =
            new HashMap<>();

    private final ReadWriteLock lock =
            new ReentrantReadWriteLock();

    public String get(String key) {

        lock.readLock().lock();

        try {

            return config.get(key);

        } finally {

            lock.readLock().unlock();
        }
    }

    public void put(String key, String value) {

        lock.writeLock().lock();

        try {

            config.put(key, value);

        } finally {

            lock.writeLock().unlock();
        }
    }

    public void reload(
            Map<String, String> newConfig) {

        lock.writeLock().lock();

        try {

            config.clear();

            config.putAll(newConfig);

        } finally {

            lock.writeLock().unlock();
        }
    }
}

Why use the write lock for reload()?

Because:

clear()
   +
putAll()

should behave as one protected update.

We don't want another thread to observe a partially updated map during this operation.

17. Important Production Mistake

Do not hold a lock while doing slow operations.

Bad:

lock.writeLock().lock();

try {

    callDatabase();

    callExternalAPI();

    Thread.sleep(5000);

    cache.put("key", "value");

} finally {

    lock.writeLock().unlock();
}

Problem:

WRITE LOCK held
        ↓
All readers blocked
        ↓
All writers blocked
        ↓
Application slowdown

Better:

// Slow operation outside lock
String data = callDatabase();

lock.writeLock().lock();

try {

    cache.put("key", data);

} finally {

    lock.writeLock().unlock();
}

Keep this small:

Acquire Lock
     ↓
Update Shared State
     ↓
Release Lock
18. Important Alternative: ConcurrentHashMap

Sometimes you don't need to manually manage a ReadWriteLock.

For a concurrent map, consider:

ConcurrentHashMap

Example:

ConcurrentHashMap<String, String> cache =
        new ConcurrentHashMap<>();

cache.put("user1", "Pradeep");

String value = cache.get("user1");

For many use cases:

ConcurrentHashMap

is better than manually doing:

HashMap
+
ReadWriteLock

However:

ConcurrentHashMap

does not automatically make a multi-step business operation atomic.

For example:

if (!cache.containsKey(key)) {
    cache.put(key, value);
}

may not represent the atomic behavior you want.

Instead, use operations designed for atomic map updates, such as:

cache.putIfAbsent(key, value);

or:

cache.computeIfAbsent(
    key,
    k -> createValue(k)
);

1. What is ReadWriteLock?

A synchronization mechanism that separates read access from write access.

1. Lambda Expressions
What is Lambda?

A lambda expression is a concise way to represent an implementation of a functional interface.

Before Java 8:

Runnable runnable = new Runnable() {
    @Override
    public void run() {
        System.out.println("Hello");
    }
};


Java 8:

Runnable runnable = () -> System.out.println("Hello");

General syntax:

(parameters) -> expression

or:

(parameters) -> {
    // statements
}

Why were lambdas introduced?

The main purpose was to enable functional programming and make behavior easier to pass around as data.

For example:

List<String> names = List.of("John", "Alex", "Bob");

names.forEach(name -> System.out.println(name));

Instead of writing an external loop.

Important point for senior interviews

Lambda doesn't create a new functional interface.

It provides an implementation of an existing functional interface.

2. Functional Interfaces

A functional interface contains exactly one abstract method.

Example:

@FunctionalInterface
interface Calculator {
    int calculate(int a, int b);
}

| Interface           | Method              | Purpose        |
| ------------------- | ------------------- | -------------- |
| `Predicate<T>`      | `boolean test(T t)` | condition      |

| `Consumer<T>`       | `void accept(T t)`  | consume        |
| `Supplier<T>`       | `T get()`           | supply         |

Example:
