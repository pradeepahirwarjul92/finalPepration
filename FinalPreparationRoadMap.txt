 ### Stack vs Heap
 
*Stack :  Every Java thread has its own JVM stack.

Conceptually:

Thread
 |
 v
Stack
 |

       |

When the method returns:
	 calculate()

Important

Thread-specific

		-	Contains operand stack information
		-	Generally much smaller than heap
		

*Heap -   The heap is the main memory area where Java objects are allocated.

Conceptually:
Stack

user
 |
 | reference
 v

Heap

+----------------+

| name           |
| age            |
+----------------+

Heap is shared among threads.

This is important.

Thread 1 ─┐
Thread 2 ─┼──→ Shared Heap
Thread 3 ─┘

Therefore concurrency issues often involve shared heap objects.

| Stack                                     | Heap                      |
| ----------------------------------------- | ------------------------- |
| Per thread                                | Shared between threads    |
| Method execution                          | Objects                   |
| Stack frames                              | Object memory             |

 ** How to Create Immutable Class
 
public final class Employee {

    private final int id;
    private final String name;

    public Employee(int id, String name) {
        this.id = id;
        this.name = name;
    }

    public int getId() {

    }

        return name;
    }
}


Important rules:
 
Rule 1 : Make class: final
Rule 2 : Fields: private final
Rule 3 : No setters.
Rule 4 : Initialize fields through constructor.
Rule 5 : Defensive copying for mutable fields.


 ** Defensive Copy

This is senior-level interview material.

Suppose:

class Employee {

    private final Date joiningDate;

    public Employee(Date joiningDate) {
        this.joiningDate = joiningDate;
    }

    public Date getJoiningDate() {
        return joiningDate;
    }
}

This is not truly immutable.

Why?

Date is mutable.

Caller can do:

Date date = new Date();

Employee e = new Employee(date);

date.setTime(...);

Now the Employee's internal state changed.

** Correct Defensive Copy

public Employee(Date joiningDate) {
    this.joiningDate = new Date(joiningDate.getTime());
}

public Date getJoiningDate() {
    return new Date(joiningDate.getTime());
}

Now callers cannot directly modify the internal object.

With modern Java, prefer immutable date/time types such as:

LocalDate
LocalDateTime
Instant

where appropriate.

Interview level:

Why prefer composition over inheritance?

Suppose you write:

class Payment {

    void pay() {
    }

    void refund() {
    }
}


Then:
class CashPayment extends Payment {
}

But suppose your business rule says:  Cash payment cannot be refunded through the system.

A better design might be:

interface Payment {
    void pay();
}

and:

interface Refundable {
    void refund();
}

Then:

class CreditCardPayment implements Payment, Refundable {

    public void pay() {
    }

    public void refund() {
    }
}

while:

class CashPayment implements Payment {

    public void pay() {
    }
}

Now only refundable payments implement:

Refundable

This is capability-based design, and it naturally avoids many LSP problems.




You might end up doing:

"Explain Liskov Substitution Principle using the Bird/Penguin example."

A strong 8-year-experience answer would be:

LSP states that a subtype should be substitutable for its parent type without changing the correctness or expected behavior of the program.

For example, if Bird has a fly() method and Penguin extends Bird, then Bird bird = new Penguin(); bird.fly(); becomes problematic because penguins cannot fly.

The problem isn't that Penguin isn't a Bird. The problem is that Bird has been given a behavior that isn't applicable to all birds.

Instead, I would keep common behavior such as eat() in Bird and model flying as a separate capability, such as a FlyingBird interface. Then Eagle and Sparrow can implement FlyingBird, while Penguin doesn't.

This keeps the abstraction behaviorally correct and allows subtypes to safely substitute their parent types.

Remember this one line:

LSP is not about whether the child "IS-A" parent in the real world; it is about whether the child can safely behave like the parent in the software design.

## 7. Thread Lifecycle

A simplified Java thread lifecycle:

NEW
 │
 │ start()
 ↓
RUNNABLE
 │
 ├───────────────┐
 │               │
 │ waiting       │ lock/sleep/wait/join
 ↓               ↓
RUNNING       WAITING / BLOCKED / TIMED_WAITING
 │               │
 └───────────────┘
        │
        ↓
    TERMINATED

The important states are:


NEW
Thread thread = new Thread();

Thread object exists but hasn't started.

State = NEW


RUNNABLE

After:

thread.start();

The thread is ready to run or currently executing.

State = RUNNABLE

The OS scheduler decides when it actually gets CPU time.

BLOCKED

A thread is waiting to acquire a monitor lock.

Example:

synchronized(lock) {
    // critical section
}

If another thread already owns lock:

Thread 1
   │
   │ owns lock
   ↓

Thread 2
   │
   └── BLOCKED

WAITING

The thread waits indefinitely for another thread/action.

Examples:

object.wait();
thread.join();

TIMED_WAITING

The thread waits for a specific amount of time.

Examples:

Thread.sleep(5000);

thread.join(5000);
TERMINATED

The run() method has completed.

public void run() {

    System.out.println("Finished");
}

After completion:

State = TERMINATED

A terminated thread cannot be started again.

This will throw an exception:

Thread thread = new Thread();

thread.start();
thread.start();

You will get:

IllegalThreadStateException

10. join()

join() makes the current thread wait for another thread to finish.

Example:


package com.heg.phase1;

public class MyTaskV2 extends Thread {
	
	public void run() {
		for(int i = 1 ; i<=5 ;i++) {
			System.out.println("Worker : " +i);
		}
	}
	
	public static void main(String[] args) {
		MyTaskV2 task = new MyTaskV2();
		task.start();
		try {
			task.join();
		} catch (InterruptedException e) {
			// TODO Auto-generated catch block
			e.printStackTrace();
		}
		
		System.out.println("Main Finished");
	}

}

OUTPUT ::
Worker : 1
Worker : 2
Worker : 3
Worker : 4
Worker : 5
Main Finished


Execution:

Main Thread
    │
    │ start worker
    ↓
Worker Thread Running
    │
Main Thread calls join()
    │
    └──── WAITING ────┐
                      │
Worker finishes       │
                      ↓
Main continues

Without join(), output order may be unpredictable.


interrupt()

interrupt() is a request to a thread to stop what it is doing.

It does not forcefully kill the thread.

13. Thread Priority

Runnable
    ↓
void run()
    ↓
No result


Callable
    ↓

3. What is Future?

Suppose you submit a task that takes 5 seconds:

Start calculation
      ↓
Working...
      ↓
Working...
      ↓
Result available

You don't have the result immediately.

Future represents:

A result that will be available in the future.

Example:

Future<Integer> future;

Think of it as a placeholder:

Future<Integer>

┌─────────────────────┐
│ Result not ready yet │
└─────────────────────┘

        ↓ Task completes

┌─────────────────────┐
│ Result = 30          │
└─────────────────────┘



public class FutureExample {
	public static void main(String[] args) {
		
		 // Create thread pool with 2 worker threads
		ExecutorService executor = Executors.newFixedThreadPool(2);
		
		Callable<Integer> task = ()-> {
			System.out.println("Task Running in : " 
							+ Thread.currentThread().getName());
		

			Thread.sleep(3000);
			return 10+20;
		};
		
		
		Future<Integer> future = executor.submit(task);
		
		
		System.out.println("Main thread continue ... ");
		
		//Wait for result 
		
		Integer result=0;
		try {
			result = future.get();
		} catch (InterruptedException | ExecutionException e) {
			// TODO Auto-generated catch block
			e.printStackTrace();
		}

		//Shutdown thread pool 
		
		executor.shutdown();
		
		
	}

5. Understand the Execution Step-by-Step

Let's debug what happens.

Step 1: Main thread starts
Thread = main


Step 2: Create ExecutorService
ExecutorService executor =
        Executors.newFixedThreadPool(2);

Now you have the ability to use worker threads.

Conceptually:

ExecutorService
│
├── Worker Thread 1
│
└── Worker Thread 2


Step 3: Create Callable
Callable<Integer> task = () -> {
    Thread.sleep(3000);
    return 30;
};

At this point:

Task created
BUT NOT RUNNING

Step 4: Submit task
Future<Integer> future =
        executor.submit(task);

Now:

Main Thread
     │
     │ submit(task)
     ↓
ExecutorService
     │
     └──────────────→ Worker Thread
                            │
                            ↓
                         task.call()

At the same time, the main thread receives:

Future<Integer>

The task and main thread can continue independently.



6. Future.get() — Very Important
Integer result = future.get();

get() means:

"Give me the result. If it is not ready, wait."

Example:

Main Thread                    Worker Thread

submit()
   │
   │                           Task running
   │                                │
future.get()                        │
   │                                │
WAITING ----------------------------│
   │                                │
   │                           Task finishes
   │                                │
   └──────────── Result = 30 ◄──────┘

So:

future.get();

is a blocking operation.


. Why Use Future If get() Blocks?

Because you don't need to call get() immediately.

Bad usage:

Future<Integer> future =
        executor.submit(task);

Integer result = future.get();

If you immediately call get(), the main thread waits.

Better:

Future<Integer> future =
        executor.submit(task);

// Do some other work here

System.out.println("Processing other work...");

// Get result only when needed
Integer result = future.get();

Flow:

Submit Task A
      │
      ├── Worker executes Task A
      │
Main Thread
      │
      ├── Do Task B
      │
      ├── Do Task C
      │
      ↓
Need Result A?
      ↓
future.get()


8. Future Methods
get()
Integer result = future.get();

Wait indefinitely.

get(timeout)
Integer result =
        future.get(5, TimeUnit.SECONDS);

Wait for a maximum of 5 seconds.

If the result is not ready:

TimeoutException

Example:

try {

    Integer result =
            future.get(5, TimeUnit.SECONDS);

} catch (TimeoutException e) {

    System.out.println("Task took too long");
}

This is important in production systems.

Example:

Order Service
      │
      ↓
Call Payment Service
      │
      ↓
Wait maximum 3 seconds
      │
      ├── Response → Continue
      │
      └── Timeout → Handle failure
9. isDone()
future.isDone();

Returns:

true

if:

Task completed successfully
Task failed
Task was cancelled

Example:

if (future.isDone()) {

    System.out.println("Task finished");
}

Important:

isDone() == true

does not always mean:

Task completed successfully

It may also mean the task failed or was cancelled.

10. isCancelled()
future.isCancelled();

Checks whether the task was cancelled.

11. cancel()
future.cancel(true);

The boolean is:

true  → Request interruption if task is running
false → Don't interrupt if already running

Example:

Future<Integer> future =
        executor.submit(() -> {

            while (true) {

                if (Thread.currentThread().isInterrupted()) {

                    System.out.println("Stopping task");

                    break;
                }
            }

            return 100;
        });

Thread.sleep(2000);

future.cancel(true);

Important:

Cancellation is cooperative.

cancel(true) does not guarantee that arbitrary code stops immediately.

The running task should respond properly to interruption.


12. Runnable vs Callable vs Future

| Feature                | Runnable          | Callable | Future                               |
| ---------------------- | ----------------- | -------- | ------------------------------------ |
| Represents task        | Yes               | Yes      | No, represents result/control        |
| Return value           | No                | Yes      | Gets result                          |
| Checked exception      | No direct support | Yes      | Reports task failure through `get()` |
| Method                 | `run()`           | `call()` | `get()`, `cancel()` etc.             |
| Asynchronous by itself | No                | No       | No — used with execution framework   |


Important relationship:

Callable
   │
   │ submit()
   ↓
ExecutorService
   │
   │ Executes task
   ↓
Future
   │
   │ get()
   ↓
Result

14. Multiple Callable Tasks

package com.heg.phase1;

import java.util.concurrent.ExecutionException;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;

public class MultipleTasksExample {

	public static void main(String[] args) throws InterruptedException, ExecutionException {
		ExecutorService executor = Executors.newFixedThreadPool(3);
		
		Future<Integer> future1 = executor.submit(
				()-> {
				Thread.sleep(3000);
				System.out.println("Task 1 finished ");
				return 10;
				});
		
		Future<Integer> future2 = executor.submit(
				()-> {
				Thread.sleep(3000);
				System.out.println("Task 2 finished ");
				return 20;
				});
		
		
		Future<Integer> future3 = executor.submit(
				()-> {
				Thread.sleep(3000);
				System.out.println("Task 3 finished ");
				return 30;
				});
		
		 System.out.println("All tasks submitted");
		 
		 int result = 
				 future1.get()
				 +future2.get()
				 +future3.get();
		 
		 System.out.println("Total = " +result);
		 
		 executor.shutdown();
		
	}
}

Possible execution:

Main Thread
    │
    ├── Submit Task 1 ──→ Worker-1
    │
    ├── Submit Task 2 ──→ Worker-2
    │
    └── Submit Task 3 ──→ Worker-3


Worker-1 → Sleep 3 seconds
Worker-2 → Sleep 2 seconds
Worker-3 → Sleep 1 second


Completion order:

Task 3
Task 2
Task 1

But the main thread calls:

future1.get();

first.

So it waits for Task 1, even though Tasks 2 and 3 may already have finished.

This is one limitation you'll later solve more elegantly with:

CompletableFuture
